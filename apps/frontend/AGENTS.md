# Frontend implementation guidelines

The frontend is a TanStack Start application running through Vite. Read the nearby source before adding a route, component, form, or API operation, and preserve the existing patterns.

## General practices

- Use TypeScript and avoid `any`. Define a props type for every component and use precise request/response types.
- Prefer named exports, `type` aliases, and normal React imports. TanStack Start/Vite framework and configuration entry points may use the default exports required by their APIs.
- Keep components modular, reusable, accessible, and easy to test. Use semantic HTML, labels, keyboard support, and ARIA only where it adds the missing relationship or state.
- Use `cn` from `src/lib/utils/cn.ts` for conditional or compound Tailwind classes; do not build class strings with interpolation. Prefer `space-*` utilities where they express layout more clearly than repeated margins.
- Prefer object literals and unions over enums. Use PascalCase for component names, camelCase for values/functions, UPPER_SNAKE_CASE for true constants, and kebab-case for file and directory names.
- Add loading skeletons for cards, charts, and other content that can take noticeable time to load.

## Routes and document metadata

- File-based routes live in `apps/frontend/src/routes`. Define each route with `createFileRoute` from `@tanstack/react-router`; keep route loaders, pending UI, error UI, and not-found UI close to the route that owns them.
- `src/routeTree.gen.ts` is generated by the TanStack Router/Vite plugin. Never edit it by hand or import a hand-maintained replacement.
- Use route-level `pendingComponent`, `errorComponent`, and `notFoundComponent` for route-specific states when needed. The root route owns the application-wide not-found fallback. Error states should give users a recoverable action and should not hide the underlying failure from logging.
- Set page metadata with a route `head` function and TanStack's current `meta` entries (for example `{ title: "Settings" }` and `{ name: "description", content: "..." }`). Keep metadata in the route definition rather than framework-specific metadata exports.
- Keep route components small. Move domain UI to `src/components/<domain>` and route-only UI to a route-owned folder/module rather than placing unrelated presentation in `__root.tsx`.

```tsx
import { createFileRoute } from "@tanstack/react-router";

export const Route = createFileRoute("/settings")({
  head: () => ({
    meta: [
      { title: "Settings" },
      { name: "description", content: "Manage your account settings." },
    ],
  }),
  pendingComponent: SettingsPending,
  errorComponent: SettingsError,
  notFoundComponent: SettingsNotFound,
  component: SettingsPage,
});

function SettingsPage() {
  return <main aria-labelledby="settings-title"><h1 id="settings-title">Settings</h1></main>;
}

function SettingsPending() {
  return <main aria-busy="true">Loading settings…</main>;
}

function SettingsError() {
  return <main role="alert">Unable to load settings.</main>;
}

function SettingsNotFound() {
  return <main><h1>Settings not found</h1><a href="/">Return home</a></main>;
}
```

## Router, SSR, and data loading

- `getRouter()` in `src/router.tsx` creates a fresh `QueryClient` and router for each request, then calls `setupRouterSsrQueryIntegration`. Preserve this per-request boundary; never create a module-level `QueryClient` singleton for SSR.
- The SSR query integration owns the `QueryClientProvider` lifecycle. Do not add a second provider around `Outlet` or route components. Use the route context's `queryClient` for loader prefetching and TanStack Query hooks for client reads.
- Keep query options and keys stable and share them between loaders and hooks. Handle pending, error, and not-found states deliberately instead of rendering undefined data.

## Environment and source layout

- Browser-exposed configuration uses Vite's `import.meta.env.VITE_*` convention. The shared API client reads `import.meta.env.VITE_API_URL`; browser code must not read server-only `BACKEND_*` secrets.
- Backend configuration remains server-only (`BACKEND_PORT`, `BACKEND_AUTH_URL`, and related values). Pass only intentionally public values through a `VITE_` variable.
- Components live under `src/components` (`ui` primitives, `forms`, and domain folders such as `auth`); shared services, hooks, and utilities live under `src/lib`. The current API boundary is `src/lib/services/api`, forms hooks are under `src/lib/hooks/forms`, and global Tailwind CSS is `src/styles/globals.css`.
- Add barrel exports only where a group already benefits from one, and update all callers when moving a module. Keep browser-only and server-only code clearly separated; do not add a suffix merely to imitate another framework.
